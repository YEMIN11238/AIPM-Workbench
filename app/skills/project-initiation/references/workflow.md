# 四阶段工作方法

来源为用户指定《需求与立项》课件和优秀规划案例。方法可复用，案例事实不可迁移。

## 前置问题与用户验证

问题定义卡包含谁、何时何地、在做什么、卡在哪、目前怎样凑合和代价。把功能建议改写为用户未被解决的问题，追问原因直到项目可改变的层面。

行为画像包括知道什么、在乎什么、什么时候用、因为什么卡住。根据项目按生命周期、频次/价值或购买动机分群；实际使用者、购买者、决策者及受影响者不同则分开。

调研先明确验证目标，再选择重度、边缘、流失或潜在人群，问过去行为。定量判断有多少人，定性解释为什么。每条结论配证据。没有真实验证材料则向用户索取，并提出调研计划，不能虚构调研总结。

## 1. 需求池

建议字段为编号、能力项、目标用户、场景、痛点与目标、建设方向、来源/提出方、证据编号、描述、验证状态、生命周期状态、依赖、负责人、预计上线。

建设方向可用增长、转化、留存、体验或适合当前项目的分类。负责人、成本和日期未知则待确认。收集时先不把全部需求标 P0。

从问题推出用户动作，再推出能力项。来源和重要性说得清的进入正式池；未经验证的想法列候选。进池不等于承诺开发，通过评审再更新状态。上线、迭代、下线保留编号和变更理由。

进入竞品阶段前，应能清楚说明用户问题和证据边界。

## 2. 竞品分析

先定目的，包括新产品是否做、存量版本先改什么、是否跟进对手或如何定价。按直接、间接、现有替代方式和潜在进入者寻找；数量由相关性决定，不强凑。潜在进入者标为风险假设。

比较维度按本次决定选择。

| 维度 | 重点 |
|---|---|
| 市场/定位 | 用户、阶段、竞争格局、价值主张、商业模式；市场规模缺数据则留缺口 |
| 用户/流程 | 完整主路径、触发场景、输出物、成功与失败、真实反馈 |
| 方案/技术 | 如何完成任务、关键依赖和能力边界；未公开架构不猜 |
| 基础/成本 | 数据来源、定价权益、集成条件和成本；价格注明地域、币种及核验日期 |

成果是横向证据表和决策结论。差异化落到具体用户、需求和场景，区分已证实的竞争限制与待验证设想。构造有说服力的失败论证，检查用户当前替代方式是否已足够；不要只列功能勾叉或泛称“更智能”。

## 3. MVP 范围

先写首版核心假设。POC验证技术门槛，原型验证理解与操作，MVP验证真实用户能否完成任务并持续使用，不混淆。

可结合 Kano 基本型/期望型/兴奋型/反向型，以及价值×成本四象限。分类须有用户证据，资料不足标初判。成本未知向用户或研发索取，不把功能数量当工时。

MVP 表包含核心假设、目标用户与场景、完整使用路径、必须做、明确不做、以后再做、依赖、验收及验证方法。每项关联需求编号和取舍理由。移除后假设仍能验证的功能考虑后移，让首版独立完成一条路径。

指标注明分母、周期、目标依据、观察窗口、取数方法及质量约束。未知目标先讨论，不写成上线承诺。验证不足后可继续验证、收缩、转向或停止，条件提前提出并与用户确认。

## 4. 立项报告

回答用户是否获得价值、公司是否获得业务价值、团队是否能实现。业务价值可以是收入、成本、留存或战略验证，不默认直接赚钱。

| 章节 | 决策内容 |
|---|---|
| 00 决策摘要 | 做/不做/有条件做，先为谁、先做什么、投入及决策条件 |
| 01 背景与问题 | 为什么现在做，现状、问题、替代方案及证据 |
| 02 用户与场景 | 用户行为、现有路径、代价、证据与样本局限 |
| 03 市场与竞品 | 竞争/替代、机会、失败论证、差异化依据 |
| 04 目标与成功指标 | 现状/目标/衡量对照、主指标、质量约束及取数口径 |
| 05 方案与第一版范围 | 专题和需求编号、先后、做/不做/后做及依赖 |
| 06 投入与计划 | 角色容量、预算依据、阶段节奏、并行关系和验收点 |
| 07 风险与停止条件 | 风险、责任边界、替代/降级、继续/转向/停止标准 |
| 附录 | 需求池、竞品证据、MVP表、证据台账、未决事项 |

优秀案例可借鉴一页结论、问题驱动专题、现状/目标/衡量对照、版本×专题及版本×角色矩阵、明确决策待办和详细附录。目录服从项目和用户模板，不为同款形式虚构漏斗或强分三专题。

投入分为用户已确认容量、研发估算和提议。日期无依据时只给明确标注的相对阶段方案，并问用户工期与锚点。预算用有出处的人工、服务、授权和基础设施输入测算；没有输入不能计算 ROI。

## AI项目附加判断

仅当当前项目涉及 AI 时分析重复性、标准化及人力瓶颈，并比较规则、流程调整和普通软件。单独写质量门槛、人工/规则对照、失败兜底、数据来源及使用权限、单次调用成本和总量假设。质量未验证可先POC，再决定MVP。按真实场景处理风险，不添加无关审批清单。
